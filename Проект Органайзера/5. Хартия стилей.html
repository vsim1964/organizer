Хартия стилей

Единые правила оформления Organizer и учебного сравнения трёх способов разработки интерфейса: собственного CSS, Bootstrap и Tailwind CSS.

17 ноября 2026 г. · Версия 1.0 · Статус: проект для утверждения через Pull Request

Предмет соглашения

HTML-разметка определяет смысл и структуру интерфейса, CSS — его вид и пространственную организацию, JavaScript — действия. Эта хартия устанавливает общую визуальную систему, соглашения об именовании, правила выбора Grid и Flexbox, принципы адаптивности и условия, при которых три реализации можно сравнивать между собой. Она не подключает библиотеки и не изменяет текущий index.html.

01. Зачем нужна хартия

К созданию стилей можно приступить сразу после завершения HTML. Однако без общих правил неизбежны случайные размеры, противоречивые имена классов и смешение разных подходов. Для учебного проекта это особенно нежелательно: будет трудно отделить свойства самого CSS от удобств, предоставляемых сторонней библиотекой.

В репозитории уже имеется структурный index.html с десятью экранами, тремя диалогами и атрибутами для будущей навигации. Его семантическая основа остаётся общей точкой отсчёта. На этапе визуального оформления допускается добавить классы и необходимые контейнеры без изменения назначения элементов, идентификаторов и состава форм. Внесённые изменения должны быть одинаково объяснимы во всех трёх вариантах.

Статус решений. До слияния документа это проект правил. После вашего утверждения он станет основанием для следующего Pull Request — реализации собственного style.css.

02. Общие принципы

Сохраняем смысловую HTML-разметку и доступные названия элементов. Не используем идентификаторы id для оформления: они связывают экраны, формы и JavaScript. Для стилизации в собственном CSS вводим классы. Одни и те же значения цвета, отступов и размеров задаются через переменные; повторять их вручную в разных компонентах нежелательно.

Начинаем проектирование с узкого экрана (mobile first), затем добавляем правила для более широких пространств. Интерфейс должен сохранять читаемость, возможность управления с клавиатуры и понятную иерархию при изменении размера окна или масштаба браузера.

Система оформления независима от серверных решений: количество пользователей, разрешения, хранение задач и способ авторизации не должны определять цвет кнопки или число колонок в списке.

03. Визуальная система Organizer

Дизайн-токен — именованное значение, например цвет фона или расстояние между элементами. В собственном CSS токен можно задать пользовательским свойством --color-accent и повторно использовать в нескольких селекторах. Токены позволят перенести одну и ту же визуальную систему в Bootstrap и Tailwind, несмотря на разницу их классов.

Шрифты и масштаб

Основной шрифт — системный стек system-ui, -apple-system, "Segoe UI", Arial, sans-serif. Он не требует скачивания внешних файлов. Базовый текст предлагается делать размером 16px при обычном масштабе, межстрочный интервал — около 1.5. Заголовки задаём через ограниченную типографическую шкалу, а не каждый раз отдельным случайным числом. Для длинных подписей допускается перенос; интерфейс не должен опираться на принудительное обрезание содержимого.

04. Соглашение об именах: БЭМ

В варианте собственного CSS принимаем упрощённую методологию БЭМ — «Блок, элемент, модификатор». Блок обозначает самостоятельный компонент; элемент — зависимую часть блока; модификатор — разновидность или визуальное состояние. Цель БЭМ здесь практическая: по имени класса должно быть понятно, какой компонент оформляется и насколько селектор зависит от структуры HTML.

<article class="task-card task-card--overdue">
  <h3 class="task-card__title">Подготовить план</h3>
  <div class="task-card__actions">
    <button class="button button--secondary">Изменить</button>
  </div>
</article>

Имена записываем латинскими буквами в нижнем регистре. Слова внутри части имени разделяются дефисом: task-card. Элемент обозначается двойным подчёркиванием: task-card__title. Модификатор — двойным дефисом: task-card--overdue. Не создаём цепочек наподобие task-card__footer__button: отдельная кнопка может быть самостоятельным блоком button, помещённым в элемент task-card__actions.

Используем БЭМ там, где компонент действительно повторяется или имеет внутреннюю структуру: оболочка app-shell, меню sidebar, карточка task-card, форма form-field, кнопка button, диалог dialog-panel. Не нужно создавать отдельный класс для каждого простого тега или каждого промежутка между элементами.

Для динамических состояний допускаем стандартные псевдоклассы :hover, :focus-visible, :disabled, а также семантические атрибуты [aria-current="page"], [aria-invalid="true"] и [hidden]. Не следует дублировать одно и то же состояние бесконечными модификаторами. Привязку JavaScript лучше строить по имеющимся data-* и id, не по названиям БЭМ-классов.

05. Где Grid, а где Flexbox

Различать эти инструменты полезнее по числу направлений компоновки, чем по уровню вложенности. Grid управляет строками и колонками одновременно; Flexbox упорядочивает элементы преимущественно вдоль одной оси. Оба инструмента можно вкладывать друг в друга.

06. Адаптивность и мобильные экраны

Вначале описываем расположение на узком экране без предположения о конкретной модели телефона. На малой ширине боковое меню не должно съедать рабочую область. Вариант для согласования: показывать компактную навигацию через кнопку меню; после раскрытия меню должно быть доступно с клавиатуры, иметь понятное имя и управляемое состояние aria-expanded. Управление открытием будет поручено JavaScript.

Начиная приблизительно с 768px, можно исследовать двухколоночную оболочку, а на широких экранах — более плотные сетки карточек. Значения 768px и 1200px принимаем как исходные контрольные точки, но не как догму: точки перестройки следует определять по тому, когда содержимому становится тесно.

Контрольная ширинаЧто проверяем

Должны работать масштабирование браузера и длинные пользовательские названия. Не рассчитываем высоты карточек так, чтобы текст выходил за их границы. Избегаем жёстких размеров, мешающих увеличенному тексту. Для сеток предпочтительнее гибкие величины minmax() и repeat(), когда они упрощают адаптацию.

07. Состояния элементов

Хартия распространяется на стандартные состояния всех интерактивных элементов. Обычное состояние должно ясно показывать, что элемент доступен для действия. При наведении (:hover) допустимо изменение фона или рамки. При фокусе с клавиатуры (:focus-visible) обязателен заметный контур. Не заменяем его одним едва различимым цветом.

У неактивной кнопки используется атрибут disabled, а у поля с ошибкой можно установить aria-invalid="true" и связать пояснение через aria-describedby. Для текущего пункта навигации подходит aria-current="page". Скрытые экраны должны использовать hidden так, чтобы не оставаться доступными для клавиатурного перехода.

Следует предусмотреть загрузку, пустые списки, успешное сохранение, ошибку сервера, просроченную задачу и обязательные поля. Не все эти состояния существуют в HTML-прототипе; здесь мы закрепляем их визуальные правила для последующего появления в коде. Цвет не должен быть единственным носителем значения: «Просрочена» или «Ошибка» сопровождаются текстом, а не только красным фоном.

08. Три способа оформления одного интерфейса

01 · Базовая реализация

Собственный CSS

Пишем style.css самостоятельно. Используем БЭМ, CSS-переменные, Grid, Flexbox и медиазапросы. Этот вариант становится эталоном для сравнения.

02 · Сопоставление

Bootstrap

Сохраняем смысловую HTML-структуру, подключаем Bootstrap и используем его сетку, компоненты и утилиты. Дополнительные стили допустимы для совпадения с общей палитрой и размерами.

03 · Сопоставление

Tailwind CSS

Используем утилитарные классы и общую тему. Применяем актуальную схему сборки Tailwind, а не смешиваем примеры разных крупных версий.

Различия не следует скрывать

Bootstrap предоставляет готовую систему компонентов и адаптивную сетку, но его стандартный ряд колонок основан на Flexbox; использование отдельного CSS Grid у Bootstrap имеет собственные условия. Официальная документация Bootstrap. Tailwind, напротив, предполагает активную композицию утилитарных классов непосредственно в HTML и генерацию необходимого CSS на этапе сборки. Официальная документация Tailwind.

Для сравнения важна методическая чистота. Вариант Bootstrap не нужно превращать в имитацию БЭМ, а Tailwind — обременять собственными классами для каждого элемента. БЭМ остаётся договорённостью для самостоятельного CSS. При этом одинаковые данные, структура экранов, язык интерфейса и принципы доступности обязательны во всех трёх вариантах.

Не подключать все три подхода одновременно. Bootstrap и Tailwind не должны конкурировать в одном документе за базовые стили. Иначе сравнение превратится в исследование конфликтов CSS, а не преимуществ методов.

09. Репозиторий, ветки и файлы

В основной ветке main сохраняется одна согласованная версия Organizer. Исследовательские варианты реализуем в отдельных ветках и при необходимости в отдельных демонстрационных каталогах. Нельзя бездумно заменять основной index.html вариантом Bootstrap или Tailwind, иначе образцовая структура приложения перестанет быть общей точкой отсчёта.

organizer/
├── index.html           # согласованная HTML-структура
├── style.css            # собственные стили (первый этап)
└── Проект Органайзера/
    ├── 1. Постановка задачи.html
    ├── 2. Требования и сценарии.html
    ├── 3. Модель данных.html
    ├── 4. Карта экранов и переходов.html
    └── 5. Хартия стилей.html

Это ближайшее состояние после реализации собственного CSS. Для Bootstrap и Tailwind имена демонстрационных каталогов и конфигурация сборки будут определены перед их созданием. Каждое изменение проходит отдельный Pull Request, а слияние в main выполняет владелец репозитория. Базовые файлы и учебные варианты не должны незаметно расходиться по функциональности.

10. Как сравнивать результаты

Три реализации следует проверять по одинаковому набору экранов и ширин. Для сравнения оцениваем не вкусовое впечатление, а наблюдаемые качества: сколько собственных правил пришлось написать, насколько HTML читаем, легко ли изменить общую палитру, насколько просто поддерживать состояния, что требуется для сборки и как ведёт себя мобильный интерфейс.

11. Вопросы, подлежащие утверждению

Предлагается утвердить системный стек шрифтов, стартовую палитру, шкалу отступов, применение БЭМ только в собственном CSS и подход mobile first. Самым существенным открытым решением остаётся устройство мобильной навигации: выдвижная боковая панель, постоянная нижняя навигация или компактное раскрывающееся меню. Для первого варианта реализации предлагается раскрывающееся меню с кнопкой и управляемым состоянием.

Вторая группа вопросов касается демонстрационных реализаций: будем ли размещать Bootstrap и Tailwind в специальных каталогах или сохранять только в отдельных учебных ветках, а также как организовать запуск Tailwind со сборщиком. Пока хартия устанавливает принцип изоляции, но не навязывает структуру каталогов без отдельного проекта.

12. Краткая хартия: что считается согласованным

Проект решения

1. Единая визуальная система. Для всех трёх подходов используются одинаковые экраны, элементы, палитра, типографика и критерии адаптивности.

2. БЭМ — для собственного CSS. Классы отвечают за оформление, идентификаторы и data-* остаются независимыми от выбранной библиотеки.

3. Grid — для двумерных компоновок; Flexbox — для одномерных. Исключения допускаются по характеру задачи.

4. Mobile first. Проверка узких экранов, фокуса клавиатуры, пустых состояний, ошибок и масштабирования обязательна.

5. Последовательность: собственный CSS → Bootstrap → Tailwind. Сначала создаём учебный эталон, затем сравниваем способы реализации.

6. Изоляция реализаций. Не подключаем три системы одновременно и не подменяем основной проект демонстрационными вариантами.

7. GitHub-процесс. Каждый этап оформляется отдельной веткой и Pull Request; main изменяется только после принятия владельцем репозитория.

Слияние этого документа обозначает принятие исходных правил оформления. При необходимости его можно уточнять отдельными предложениями, сохраняя сведения о том, почему изменилось то или иное решение.
