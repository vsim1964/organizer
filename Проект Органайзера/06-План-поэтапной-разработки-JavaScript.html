1. Как будет устроен JavaScript в Organizer

Модель MVC разделяет программу на три области ответственности. Model (модель) хранит и обрабатывает данные о задачах и проектах. View (представление) отвечает за отображение экранов, карточек, таблиц и диалоговых окон. Controller (контроллер) получает действия пользователя, обращается к модели и инициирует обновление представления.

ModelДанные и правила их изменения
ControllerОбработка событий и координация
ViewDOM, экраны и визуальное состояние

Например, при нажатии кнопки создания задачи контроллер получает событие, проверяет введённые значения и передаёт данные модели. Модель добавляет задачу в массив. После этого представление обновляет список задач. На первых уроках полноценная модель ещё не понадобится: для переключения экранов достаточно представления и контроллера. Не будем придумывать искусственную модель только ради соблюдения схемы.

Под функциональным стилем на данном этапе понимаем организацию программы преимущественно с помощью функций и модулей. Это не требование писать весь код в строгом стиле функционального программирования.

2. Этап I. Интерфейс и навигация

Сначала заставим уже существующие элементы HTML реагировать на действия пользователя. На этом этапе не подключаем сервер, не сохраняем задачи и не реализуем регистрацию.

Шаги 1–4

  1. Подключение JavaScript и DOM.

    Проверяем подключение script.js, изучаем объектную модель документа (DOM), поиск элементов с помощью querySelector() и querySelectorAll(), назначение идентификаторов и атрибутов data-*. Результат: скрипт находит и изменяет элемент страницы.

  2. Переключение экранов.

    Изучаем событие click, addEventListener(), dataset и hidden. Подключаем навигационные элементы с data-screen-target и следим, чтобы одновременно отображался один основной экран. Результат: переход между разделами Organizer.

  3. Состояние навигации.

    Добавляем выделение активного раздела, возврат из вложенных экранов и корректную обработку неизвестного идентификатора. Результат: последовательная и предсказуемая навигация.

  4. Диалоговые окна.

    Изучаем HTML-элемент dialog, методы showModal() и close(). Открываем окна по data-dialog-target, закрываем по data-close-dialog. Результат: работающие окна без сохранения данных.

3. Этап II. Модель задач

Когда навигация заработает, переходим к содержанию приложения. Задачи сначала существуют только в памяти браузера. Это позволит изучить объекты, массивы и функции до знакомства с постоянным хранением данных.

Шаги 5–9

  1. Задача как объект JavaScript.

    Определяем свойства задачи согласно утверждённой модели данных; изучаем объекты, массивы, идентификаторы. Результат: учебный массив задач.

  2. Отображение списка.

    Строим карточки и строки таблицы на основе массива, обновляем содержимое интерфейса, показываем пустое состояние. Результат: список создаётся из данных, а не из заранее написанных карточек HTML.

  3. Создание задачи.

    Изучаем submit, preventDefault(), чтение значений полей и проверку ввода. Добавляем новую задачу в массив. Результат: созданная задача появляется на экране.

  4. Редактирование и удаление.

    Находим задачу по идентификатору, изменяем свойства, подтверждаем удаление и обновляем интерфейс. Результат: полный учебный цикл изменения одной задачи.

  5. Поиск, фильтрация и сортировка.

    Изучаем filter(), find(), sort() и события полей формы. Результат: управление отображаемым списком без изменения исходных данных при фильтрации.

4. Этап III. Проекты и взаимосвязи

Следующий шаг — перейти от отдельных задач к структуре менеджера проектов. Все решения о членстве, ролях и правах сверяем с проектной документацией, не закрепляя случайные предположения в коде.

Шаги 10–13

  1. Модель проектов.

    Описываем проект, создание проекта и связь задач с проектами. Результат: работающий учебный список проектов и связанных задач.

  2. Карточка проекта.

    Показываем сведения о проекте и его задачах, организуем переходы к связанным объектам. Результат: отдельный экран проекта с данными из модели.

  3. Участники проектов.

    Отображаем пользователей, назначаем исполнителей и обрабатываем допустимые действия участников в рамках согласованной модели. Результат: клиентская демонстрация связей пользователей с проектами и задачами без претензии на серверную защиту прав.

  4. Календарь задач.

    Группируем и отображаем задачи по датам, переходим из календаря к задаче. Результат: календарный способ просмотра существующих данных.

5. Этап IV. Модули, состояние и локальное хранение

К этому моменту появится достаточно реального кода, чтобы осмысленно разделить его на модули. Не будем начинать с абстрактной структуры, которую ещё нечем наполнить.

Шаги 14–17

  1. Выделение модулей MVC.

    Разносим накопленные функции по файлам модели, представления и контроллера. Изучаем export и import. Результат: те же работающие возможности с более ясным распределением ответственности.

  2. Единое состояние приложения.

    Согласуем выбранный экран, текущий проект, редактируемую задачу и другие необходимые данные. Результат: части интерфейса не противоречат друг другу.

  3. Локальное хранение.

    Знакомимся с localStorage, JSON.stringify() и JSON.parse(). Результат: учебные задачи сохраняются между перезагрузками.

  4. Проверка клиентской версии.

    Проверяем навигацию, формы, операции с задачами, пустые состояния и ошибки. Сверяем реализованное с проектными требованиями. Результат: завершённый учебный клиентский этап.

Граница учебного этапа. localStorage не является заменой серверной базы данных и не обеспечивает многопользовательский доступ или контроль прав. Для полноценного Organizer затем потребуются API, серверная логика, база данных, регистрация, авторизация и проверка полномочий.

6. Как будут появляться модули

Первые уроки можно выполнять в небольшом script.js, отделяя функции по назначению. Когда появится потребность в нескольких файлах, ориентировочная структура станет такой:

organizer/
├── index.html
├── style.css
└── js/
    ├── app.js
    ├── models/
    │   ├── taskModel.js
    │   └── projectModel.js
    ├── views/
    │   ├── navigationView.js
    │   ├── taskView.js
    │   └── dialogView.js
    └── controllers/
        ├── navigationController.js
        └── taskController.js

Названия условны. Файлы создаются по мере необходимости; структуру можно уточнять без изменения принятых архитектурных принципов. Альтернативные реализации — ООП + MVC, функции + MVP, ООП + MVP — размещаются отдельно от основного приложения и повторяют уже освоенные сценарии.

7. Порядок работы над каждым шагом

Перед началом задания проверяем текущую ветку main в репозитории vsim1964/organizer и соответствующие проектные документы. Затем объясняем все новые термины и конструкции JavaScript, показываем их назначение в Organizer и реализуем только одну ограниченную возможность.

После этого проверяем синтаксис и поведение в браузере, разбираем код и оформляем изменение в отдельной ветке через Pull Request. Слияние с main выполняет владелец проекта. Следующий шаг начинается после проверки предыдущего.

Позднее повторяем уже решённую задачу в альтернативных реализациях, чтобы сравнить функции и классы, MVC и MVP без одновременного создания четырёх полноценных приложений.

8. С чего начинаем

Первый практический урок — подключение JavaScript и знакомство с DOM. Пока не создаём всю навигацию. Проверяем связь HTML и JavaScript, находим элемент страницы и меняем его свойство. На втором уроке используем эти знания для перехода между экранами.

Полный план состоит из 17 шагов в четырёх этапах. Его задача — превратить готовую HTML-структуру в работающий интерфейс, последовательно изучая язык и устройство приложения.
